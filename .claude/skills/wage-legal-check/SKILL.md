# wage-legal-check — 賃金の法定チェックの知識マップ

給与の支払いが労基法37条 (割増賃金) と最低賃金法を満たしているかを、給与大臣 DB の支払い実績と
勤怠 DB の時間から判定するための前提知識。**判定の実装は本リポではなく `ohishi-exp/nuxt-dtako-admin`
にある** — まずそこを取り違えないこと。

## 0. 金額を計算しているのはこのリポジトリではない

| 何 | どこ | 備考 |
|---|---|---|
| 時間 (拘束・実働・時間外・深夜) | **本リポ `/api/kintai/kosoku-daily`** (`src/kosoku.rs`、社内 MariaDB 直読み) | **打刻基準。時間の出どころはここに統一** (2026-07-28 決定) |
| 暦日按分 | nuxt-dtako-admin `workers/dtako-scraper-relay/src/kosoku-daily.ts` | 上流 (本リポ) は勤務を**始業日へ丸ごと寄せて**返す。暦日へ配るのは下流 |
| 賃金 (金額) | nuxt-dtako-admin `workers/dtako-scraper-relay/src/restraint-wage.ts` (`computeWageRow`) | **本リポには無い。** R2 の拘束アーカイブを材料に計算する |
| 支払い実績との突合 | nuxt-dtako-admin `app/utils/salary-compare.ts` (ブラウザ内) | 給与明細 × wage-report |
| 給与明細の生データ | **本リポ `/api/kyuyo/*`** (`src/kyuyo/`) | 給与大臣 SQL Server (`KYDATA{会社4桁}_{年度3桁}C`) |

→ `src/kosoku.rs` の丸め・勤務の切り方・24時間の扱いを変えても **賃金額には波及しない**。
影響が出るのは紙のタイムカード表との突合 (`src/kosoku_paper.rs`)・画面表示・改善基準告示の
遵守判定のほう。**「賃金への波及」を理由に kosoku 側の修正を止めない。**

## 1. 法定の3本柱

| 法令 | 何を決めるか | 判定 |
|---|---|---|
| 労基則19条 | 割増賃金の基礎となる **1時間あたりの賃金額** (= 基礎単価) の出し方。**賃金の定め方ごとに分母が違う** | §2 |
| 労基法37条 | 時間外 1.25 / 法定休日 1.35 / 深夜 +0.25、月60時間超は 1.5 | 支払った残業代の**合計** ≥ 基礎単価ベースの理論値の合計 |
| 最低賃金法4条3項 | **割増賃金は最低賃金の対象賃金から除外**して比較する | 最低賃金対象賃金 ÷ 所定労働時間 ≥ 都道府県別最低賃金 |

- **残業は合計で比較する** (2026-07-30 ユーザー決定) — 残業単価を逆算して倍率で判定する形は採らない。
  単価不足と時間不足の切り分けは「打刻から計算した残業時間 vs 給与明細の残業時間」の 2 列で行う。
- 最低賃金は**都道府県別**。拠点名から県を推定してはいけない (「本社」は**長崎県**)。
  未設定は未設定のまま警告し、誤った県で判定しない (nuxt-dtako-admin#409)。

## 2. 1時間あたりの賃金額 — 分母は給与区分で違う

`SHAIN3.KKUBUN` (§3) ごとに労基則19条の規則が変わる。**まとめて実働時間で割ってはいけない** —
月給者は忙しい月ほど単価が下がって37条判定が緩み、暇な月は逆に厳しくなる。

| 区分 | 分母 | 根拠 | 材料 |
|---|---|---|---|
| 1 月給 | 月平均所定労働時間 = 年間所定労働日数 × 1日所定 ÷ 12 | 19条4号 (月によって異なる場合は1年平均) | 年間所定労働日数 (**未整備**) + `work_schedules.daily_work_minutes` |
| 2 日給 | 出勤日数 × 1日所定 | 19条2号 (日給 ÷ 1日の所定労働時間) | 出勤日数 (`KINDATA*` → `/api/kyuyo/payroll` の `attendance`) + `daily_work_minutes` |
| 3 時給 | 所定内の実働時間 | 19条1号 (時間給はその額) | `wage-report` の `minutes.statutory` |
| 4 その他 / 0 未設定 | — | — | **null (判定しない)** |

- **不明を日給に倒さない。** 既定を置くと「月給者に日額計算を掛ける」壊れ方が再発する
  (nuxt-dtako-admin#429 で実害: 基本給 165,000 の月給者に 2,640,000)。
- 分母が引けない行は**判定対象から外す**。「適合」と混ぜない — 設定不足を適合と読ませない。
- 分子は支給項目の区分で決まる (§5)。基礎単価の分子は割増基礎算入分、最低賃金判定の分子は
  最低賃金対象賃金で、**同じ分母・違う分子**。

## 3. 材料 — どの列か、そして何がまだ取れないか

| 値 | 出どころ | 状態 |
|---|---|---|
| 給与区分 (月給/日給/時給) | **`SHAIN3.KKUBUN`** (`SHAIN1.INCODE` = `SHAIN3.INCODE` で結合) | `/api/kyuyo/employees` の `kkubun` で提供済み (#101) |
| 支給・控除の金額 | `KYUYO.MONEY00..79` (項目番号 018〜097) | `/api/kyuyo/payroll` で提供済み |
| **勤怠日数・残業時間** | `KYUYO.KINDATA0000, KINDATA0100, … KINDATA1600` (17列・100刻み、項目番号 001〜017) | `/api/kyuyo/payroll` の `attendance` で提供済み (#103/#104)。項目名 → **`/100` 済みの実数**、0 は含めない・同名は合算 |
| 項目名 | `KOUMOKU.TAIKEIKOUNO` = 体系コード2桁 + 項目番号3桁 | `fetch_koumoku` が絞り込みなしで全件読むので**名前だけは既に手元にある** |
| 所属・職種 | `SHOZOKU.INCODE` / `NAME1` (営業所) / `NAME2` (職種) | `SNAME` から切り出す必要はない |
| 入社日 | `SHAIN2.DAYNYU` (`SHAIN1` ではない) | 退社日の未設定は **1970-01-02 センチネル** |
| 所定労働時間 (1日) | nuxt-dtako-admin D1 `work_schedules.daily_work_minutes` (拠点・職種・適用開始日つき履歴、既定 7.5h) | 本リポには無い |
| 年間所定労働日数 | — | **どこにも無い。月平均所定を出すには新設が必要** |
| 時間 (実働・時間外・深夜) | 本リポ `/api/kintai/kosoku-daily` | 打刻基準 (§0) |

`KINDATA*` の要注意点:

- **`raw = 実数 × 100` の固定小数点 int** (全社・全項目)。`raw / 100` で実数に戻る。
  **回数系まで ×100** — 遅刻回数 `800` = 8 回。「日数と時間だけ割る」と 800 回になる。
- **`KOUMOKU.NUMMODE` (1/2/3/4) は罠。** 「表示モード」という名前でスケール区分に見え、同じ項目
  (残業時間) でも会社によって値が違うが、**給与大臣 UI の表示書式で格納スケールとは無関係**。
  参照してはいけない。`NUMMODE` によらず一律 `/ 100`。
- **かつては給与DB 経路で返っておらず**、貼り付け CSV の【 勤怠 】セクションだけが出どころだった。
  #103/#104 で**両経路とも埋まる**。応答の `attendance` は **optional のまま** — この項目を返さない版の
  本サービスが動いている環境でも取り込みを失敗させないため (デプロイ順に依存しない)。
- **日給者の分母 (§2) はこれで引ける。** ただし項目自体が無い会社・月では null になるので、
  「0 日」と「欄が無い」を取り違えないこと (0 は `attendance` に載せない仕様)。

## 4. 賃金区分と倍率 (`wage-report` / `get_wage_report` MCP)

`wage.minutes` には**性質の違う 2 種類**が混ざっている。

- **時間区分** (`workingMinutes` を完全分割): `statutory` 1.0 / `overtime` 1.25 /
  `overtimeNight` 1.5 / `legalHoliday` 1.35 / `legalHolidayNight` 1.6 /
  `weekly40Excess` 1.25 / `nonLegalHoliday` 1.25 / `nonLegalHolidayNight` 1.5
- **上乗せオーバーレイ** (時間の合計に入らない): `night` 0.25 **のみ**。所定内労働のうち深夜帯に
  当たる分への割増で、常に `night ≤ statutory`。

金額は `分/60 × 時給 × 倍率` の四捨五入、`totalAmount` は全項の単純合計。
2026-01〜06 + 2025-11/12 の **685 乗務員月**で実測し全件成立。**深夜と時間外深夜の二重計上は 0 件。**

- `summary` は深夜を **2 区分** (`nightMinutes` / `overtimeNightMinutes`) しか持たないが、賃金側は
  **4 区分**持つ。**法定休日に働いた深夜分が summary の 2 区分の両方から抜けて `legalHolidayNight`
  へ移る**ため 685 件中 321 件で数字が違って見える。差は常に一方向で、
  `(summary深夜 − wage深夜) + (summary時間外深夜 − wage時間外深夜) = wage法定休日深夜 + wage法定外休日深夜`
  が厳密に成立する (所定内か時間外かの判定は一致している)。
- `summary.days[]` の `day` は暦日ではなく**勤務の開始日ラベル**。同じ `day` が 2 回出る行がある。
- 週40超過は法定内から控除済み (二重計上なし)。月60時間超 1.5 倍は**最低賃金換算の残業代理論値だけ**に
  適用されている (単価マスタ換算側は係数一定)。

## 5. 支給項目の 5 区分

給与明細の支給項目を「割増賃金の基礎 (37条) × 最低賃金の対象 (4条3項)」の 2 軸で分類する。

| 区分 | 割増基礎 | 最低賃金対象 | 例 |
|---|---|---|---|
| base | ○ | ○ | 基本給・職務手当 |
| overtime | — (割増そのもの) | × | 残業・深夜・休日出勤手当 |
| minwage-only | × | ○ | 住宅・別居・子女教育手当 |
| premium-base-only | ○ | × | 精皆勤手当 |
| excluded | × | × | 通勤・家族手当、臨時の賃金、賞与 |

37条の除外は**限定列挙** (家族・通勤・別居・子女教育・住宅手当 / 臨時の賃金 / 1か月を超える期間の
賃金の 7 つ) なので、区分設定がこれと一致しているかは実データで確認する必要がある。

**月の突合**: 給与明細の「給与・賞与名」の年月 (例 `2026年 8月`) は**支給月ラベル**。当社は
月末締め・翌月払いのため、**勤務月 m に突合するのは m+1 月ラベルの行**。

## 6. 罠

- **tiberius の `try_get` は CAST 必須** — 型が合わないと `Err` が既定値に化けて静かに壊れる
  (`kkubun` が全員 0 になる形で 2 回踏んだ)。
- **`SHOZOKU.TAIKEI` (「体系N」) で給与区分は判定できない。** 部署に紐づく別軸で、同じ TAIKEI=1
  (乗務員) でも月給/日給/時給が混在する。相関が**大半の行で成り立ってしまう**ため、数件の
  サンプルでは正しく見えて本番で崩れる。本番 183 名は 月給 54 / 日給 121 / 時給 8。
- **乗務員CD = 一番星の社員コード**で同一番号体系。ただし給与コード 複数 → 1 人 (N:1) が現実に発生する。
- 給与大臣 DB は SQL Server 2008 R2 で、新しい OpenSSL とは TLS ハンドシェイクできない。
  調査は ohishi-data から `MinProtocol=TLSv1` + `SECLEVEL=1` を効かせた `sqlcmd`
  (詳細は `docs/kyuyo-daijin-schema.md`)。
- 現行 4 社 (0100/0200/0300/0400) は**完全に同一スキーマ**。廃業した 0500/0900 は別形。
- **本番 DB は設定変更・再起動も不可。** 対策はコード側で完結させる。例外は SELECT GRANT のみ
  (ユーザーが実行)。読み取り調査は可。

## 7. 未決 (判定に影響する)

1. **法定休日労働 (1.35) が37条理論値に入っていない** — 理論値は時間外・時間外深夜・週40超過だけを
   見ている。休日手当を残業扱い項目に入れている行では差が過大 (= 適合寄り) に出る **見逃し方向**の
   誤り。実データで法定休日労働のある人数を数えてから決める。
2. **判定を relay (front) と rust のどちらに置くか** — 現状は front (ブラウザ内)。MCP で人数を
   数えるには同じ計算が relay 側に要る。
3. **日給者の分母を給与側の出勤日数にするか、打刻の稼働日数にするか** — 支払い実績から逆算するなら
   給与側が筋だが、給与側と打刻側の日数はもともと食い違う前提。
