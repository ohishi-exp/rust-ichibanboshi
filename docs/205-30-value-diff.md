# #205-30 共通キー 65 行の値差 — 原因と判断材料

2026-06。キー = `乗務員CD|暦日|開始時刻`、乗務員CD 0 は除外 (基準にだけ 19 行)。
基準 (オンプレ `/api/kintai/kosoku-daily`) 3,372 行 / GCP (`kintai_fold` の
`day_summaries`) 3,230 行、共通キー 3,229 件のうち **65 件で値が違う**。

欠落 143 行 / 余分 1 行は別タスク (#205-19 / #205-29) の担当。ただし**余分 1 行は
この 65 行と同一原因**だったのでここで扱う (後述の C)。

## 結論 (先に 4 行)

1. **畳むコードは同じ。** オンプレの生イベントを現行コードで畳み直すと基準と
   **1 行残らず一致**する (実測。下の「土台の確認」)。よって差は入力だけ
2. **原因は 2 つある。** `shift_source` 反転 28 行は **打刻が月境界で欠ける**
   (push と fold の窓が違う)。休憩差 32 行と拘束暴発 4 行は **`dtako_events` の
   置き場が両経路で違う**
3. **反転 28 行は GCP が誤り**と言い切れる。オンプレにしか無いのではなく、
   **GCP の入力が構造的に欠ける** (再現テストあり)
4. **拘束暴発 4 行も GCP が誤り** (実在しない 1.0〜6.5 日の拘束)。休憩差 32 行の
   正否だけは、この 2 本の JSON からは決められない

## 土台の確認 — 両経路は同じコードで畳んでいる

基準 JSON はローカルで畳んだものではなく、**オンプレのサービスが
`/api/kintai/kosoku-daily` で返した結果**なので、`logic_version` が割れている
可能性があった。潰した:

`GET /api/kintai/events?month=2026-06&driver=1021` の生イベント **578 行**を
このブランチの現行コードで畳むと、**基準の 34 行と 1 行残らず一致**した
(`tests/kintai_205_30_replay_test.rs`)。#205-19 が 1078 / 1071 / 1049 で
得たのと同じ結果で、**version 差はこの 65 行に効いていない**。

## C — `shift_source` 反転 28 行: 打刻が月境界で欠ける

**push と fold の窓が違う。**

| | 関数 | 窓 |
|---|---|---|
| 書く (`kintai_push::push_month`) | `exact_month_range` | **`[月初, 翌月初)`** (`src/kintai_repo.rs:309`) |
| 読む (`kintai_fold`) | `month_range` | **`[月初, 翌月 2 日)`** (`src/kintai_repo.rs:324`、呼び出しは `src/kintai_fold.rs:938`) |

ずれの 1 日ぶん (`07-01`) は **7 月の push でしか書かれない**
(`src/kintai_push.rs:852-861`)。**7 月がまだ push されていなければ、6 月の fold は
月を跨いだ勤務の終業打刻を読めない。** `src/kintai_fold.rs:910-911` は窓が違うことを
承知で書いているが、**そこにデータが在ることは誰も保証していない**。

### 乗務員 1021 の実データ

月内の打刻は 8 件だけで、最後の 2 件が:

```
2026-06-21 06:12:34  始業
2026-07-01 14:54:29  終業     ← 相手はここ (10.4 日の勤務)
```

- **オンプレ**: MariaDB を `month_range` で直読みするので終業が見える。
  1 本の 10.4 日の勤務 → `split_long_shift` (`src/kosoku.rs:953`) が休息で割り直し、
  **欠片は元の `source` を引き継ぐ** (`src/kosoku.rs:981` / `:1064`) ので
  06-21〜06-30 が全部 `timecard`
- **GCP**: Postgres に 07-01 の行が無い → 対の無い始業として `next_rest_start`
  (`src/kosoku.rs:608`) が最初の休息 (06-21 17:44) で閉じる。翌日以降は
  `shifts_from_rest` (`src/kosoku.rs:701`) が組むので `rest`

**割れ目に使う休息と、休息由来の勤務の両端は同じイベント**なので、
**11 列は 1 分も動かずラベルだけ反転する。** 初日だけ 20 分ずれるのも必然で、
閉じる側は始業打刻から始まり中の休息が `rest_minus` に出る / 割る側は休息の後から
始まる:

```
基準: 1021|2026-06-21 06:32:00  timecard restraint=672 working=520 rest_minus=0
GCP : 1021|2026-06-21 06:12:00  timecard restraint=672 working=520 rest_minus=20
```

## A / B / D / E — `dtako_events` の置き場が違う

入力の 3 つの `source` のうち、C で見たとおり `timecard` / `dtako` は
**push の窓で欠けうる**。残る `dtako_events` は push を通らず、**両経路が別の
置き場から読む**:

| source | 中身 | オンプレ | GCP |
|---|---|---|---|
| `timecard` | 始業 / 終業 | MariaDB `time_card_dstate` | Postgres (push、**窓が 1 日狭い**) |
| `dtako` | 運行開始 / 運行終了 | MariaDB `time_card_dtako` | 同上 |
| **`dtako_events`** | **休憩 / 休息 / 運転 …** | **MariaDB `dtako_events` 表** | **alc/R2 の `KUDGIVT.csv`** |

(`src/kintai_http_repo.rs:16-52` の対応表。#205 の決定 5 で GCP は alc から直接引く。)

### A / B — 休憩の増減 (`restraint` が動かない 32 行)

- 拘束は `勤務の区間 − 中の休息` で決まり、**休憩イベントを一切見ない**
  (`src/kosoku.rs:1574-1613`)
- 休憩は「10 分以上の `休憩` イベント」を勤務内へ切り詰めて合算したもの
  (`src/kosoku.rs:1211-1225`)

⇒ **`restraint` が同値で `break` だけ違う = 勤務の両端も中の休息も同じ = 違うのは
`休憩` イベントそのもの。** (両端が同じなので、C のような打刻の欠けでは説明できない。)
他に `break` を動かす経路は「運行に出ていない勤務の昼休憩 / 夜勤の 60 分」
(`src/kosoku.rs:1618-1632`) しかないが、**32 行すべてでその値と一致しない**ので
除外できる (基準側の勤務の両端から昼休の窓の重なりを計算して GCP の
`break_minutes` と突合済み。休憩差のある 36 行のうち一致したのは D に含まれる
`1194|06-17` の 60 分 1 行だけ)。

再現: `..::one_extra_break_event_moves_break_and_working_only`

**保存側でこのフラグを見れば、値を突合しなくても壊れた行を検出できる。**

### E — 拘束 1 分差 (1 行)

紙丸めは**区分ごとに秒を切り捨てる** (`src/kosoku.rs:1451-1546`)。区分の切れ目は
運行イベントで決まるので、イベントが 1 件増減すると ±1 分ずれる。最小サイズの同型。

## 「どちらが正か」の判断材料

- **C の 28 行は GCP が誤り。** 打刻が構造的に欠けている (再現済み)。
  ただし**値そのものは 11 列とも同じ**なので、影響は今のところラベルだけ。
  **危ないのはこの 1 日の窓が値を動かす場合** — 例えば月跨ぎ勤務の終業が
  07-01 にあり、それを見るかどうかで勤務の**長さ**が変わるケースは、
  1021 ではたまたま休息の割れ目と一致して打ち消し合っただけ
- **D の 4 行も GCP が誤り。** 実在しない 1.0〜6.5 日の拘束
- **A / B の 32 行 (合計 +1,152 分) は決められない。** GCP にだけ在る `休憩` が
  本物ならオンプレが実働をそのぶん多く払っており、逆なら GCP が少なく見ている。
  **どちらの `dtako_events` が真かは、両方の生行を突き合わせないと分からない**

## 直すべきか

**`src/kosoku.rs` に直すところは無い** (#205-19 と同じ結論)。閉じられない勤務を
捏造せず捨てる/閉じる、という判断は意図どおりで、C も D も入力が欠けた結果。

直す先は入力側と検知側:

1. **(C の根治) push の窓を fold の窓に合わせる。** `push_month` が
   `exact_month_range` で書く限り、6 月の fold は 7 月の push に暗黙に依存する。
   窓を `month_range` に広げるか、fold が「読む窓ぶんの push が済んでいるか」を
   確かめて済んでいなければ **loud fail する**かのどちらか。
   **`exact_month_range` を選んだ理由は `src/kintai_push.rs:852-857` に書いてある**
   (翌月頭 2 日を「その 2 日しか見ていない状態」で署名すると毎回書き直しになる) ので、
   単純に広げるのは署名の設計と衝突する — **設計判断が要る**
2. **(D の検知) `over_24h` を fold の warning に出す。** 保存時点で
   「拘束 6.5 日」と分かる。値の突合をしなくても月次で拾える最も安い網
3. **(A / B) `dtako_events` の両側の突合。** 月ゲート (etags) は R2 の遅れしか
   見ないので、MariaDB 側にだけ無い行は拾えない

いずれも `src/kosoku*` / `src/kintai*` / `src/routes/kintai*` を触ると
`logic_version` が変わり全乗務員が stale になるので、**着手は親の判断待ち**。
