# #205-30 共通キー 65 行の値差 — 原因と判断材料

2026-06。キー = `乗務員CD|暦日|開始時刻`、乗務員CD 0 は除外 (基準にだけ 19 行)。
基準 (オンプレ `/api/kintai/kosoku-daily`) 3,372 行 / GCP (`kintai_fold` の
`day_summaries`) 3,230 行、共通キー 3,229 件のうち **65 件で値が違う**。

欠落 143 行 / 余分 1 行は別タスク (#205-19 / #205-29) の担当。ただし**余分 1 行は
この 65 行と同一原因**だったのでここで扱う (後述の C)。

## 結論 (先に 3 行)

1. 65 行はすべて **入力の `dtako_events` (デジタコの区間イベント: 休憩・休息・運転…)
   が両経路で違う**ことで説明できる。`kosoku.rs` に不具合は見つかっていない
2. 違いは**両方向**に出る — GCP にだけ在る行 (→ 休憩が増える / 勤務が早く閉じる) と、
   GCP に無い行 (→ 休憩が消える / 勤務が閉じられず数日ぶんに膨らむ) が同じ月に混在する
3. **どちらが正かは、この 2 本の JSON からは決められない。** ただし GCP 側に
   **拘束 24 時間超が 4 行 (最大 6.5 日 = 9,404 分)** 出ており、これは明らかに壊れた値
   (下記 D)。少なくともこの 4 行については GCP が誤り

## なぜそうなるか — コード上の根拠

両経路は**同じ [`daily_summary`](../src/kosoku.rs) を通る** (`kintai_fold.rs:13-27` が
読み出し経路と同じ手順で呼ぶと書いてある)。よって差は入力だけ。入力の 3 つの
`source` のうち、**割れうるのは `dtako_events` だけ**:

| source | 中身 | オンプレ | GCP |
|---|---|---|---|
| `timecard` | 始業 / 終業 | MariaDB `time_card_dstate` | Postgres (`kintai_push` が同じ MariaDB から押した行) |
| `dtako` | 運行開始 / 運行終了 | MariaDB `time_card_dtako` | 同上 (`休息` だけ運ばない) |
| **`dtako_events`** | **休憩 / 休息 / 運転 …** | **MariaDB `dtako_events` 表** | **alc/R2 の `KUDGIVT.csv`** |

(`src/kintai_http_repo.rs:16-52` の対応表。`dtako_events` は push を経由せず
GCP が alc から直接引く = #205 の決定 5。)

### A / B — 休憩の増減 (`restraint` が動かない 32 行)

- 拘束は `勤務の区間 − 中の休息` で決まり、**休憩イベントを一切見ない**
  (`src/kosoku.rs:1574-1613`)
- 実働 = 拘束 − 休憩 で、休憩は「10 分以上の `休憩` イベント」を勤務内へ切り詰めて
  合算したもの (`src/kosoku.rs:1211-1225`、閾値は `KosokuParams::break_threshold_minutes`)

⇒ **`restraint` が同値で `break` だけ違う = 勤務の両端も中の休息も同じ = 違うのは
`休憩` イベントそのもの。** 他に `break` を動かす経路は「運行に出ていない勤務の
昼休憩 / 夜勤の 60 分」(`src/kosoku.rs:1618-1632`) しかないが、**32 行すべてで
その値と一致しない**ので除外できる (基準側の勤務の両端から昼休の窓の重なりを
計算して GCP の `break_minutes` と突合済み。休憩差のある 36 行のうち一致したのは
D に含まれる `1194|06-17` の 60 分 1 行だけで、A / B の 32 行には 1 件も無い)。

再現: `tests/kintai_205_30_value_diff_test.rs::one_extra_break_event_moves_break_and_working_only`
— 25 分の `休憩` を 1 件足すと `break +25` / `working −25` / `restraint` 不変。

### C — `shift_source` の反転 (11 列同値で `timecard → rest` が 28 行)

**これが一番はっきりした形で、(c) の「20 分ずれた余分 1 行」も同じ原因。**

対になる `終業` が無い `始業` は、**次の休息の開始で閉じる**
(`src/kosoku.rs:570-580` → `next_rest_start` は `src/kosoku.rs:608-615`)。

- **休息が在る側**: 勤務はその休息で閉じる。翌日以降は
  `shifts_from_rest` (`src/kosoku.rs:701-757`) が組むので `source: rest`
- **休息が無い側**: 同じ始業から **1 本の >24h 勤務**ができ、
  `split_long_shift` (`src/kosoku.rs:953-1001`) → `split_by_run_gaps`
  (`src/kosoku.rs:1030-1080`) が「運行終了 → 次の運行開始が 8 時間以上空いた所」で
  暦日ごとに割り直す。**割れた欠片は元の `source` を引き継ぐ**
  (`src/kosoku.rs:1064`) ので、全部が `timecard` のまま残る

デジタコの休息はふつう「運行終了 → 次の運行開始」そのものなので、**割れ目の時刻が
休息由来の勤務の両端と一致する** — だから 11 列が 1 分も動かないまま `shift_source`
だけ反転する。

**初日だけは 20 分ずれる**、というのもこの形の必然:

- 割らない側 = 勤務は始業打刻から始まり、始業を跨いで終わる休息が
  `rest_minus_minutes` に出る
- 割る側 = 勤務は休息の**後**から始まるので `rest_minus_minutes` は 0

実データがまさにその形だった (基準が「割った側」、GCP が「割らない側」):

```
基準: 1021|2026-06-21 06:32:00  timecard restraint=672 working=520 rest_minus=0
GCP : 1021|2026-06-21 06:12:00  timecard restraint=672 working=520 rest_minus=20
```

再現: `tests/kintai_205_30_value_diff_test.rs::missing_rest_flips_shift_source_without_moving_any_minute`
— 同じ打刻・同じ運行イベントで**夜の休息だけを抜く**と、
`timecard`×5 日 (初日 06:32 始まり / `rest_minus` 0) ↔ `timecard`+`rest`×4 日
(初日 06:12 始まり / `rest_minus` 20) になり、**2 日目以降の 11 列は完全一致**。

⇒ **C の 28 行は「GCP 側にだけ在る休息」で説明できる**
(GCP の勤務がそこで閉じ、基準側は閉じずに走り続けて割り直された)。

### D — 拘束の暴発 (4 行)

| 行 | 基準 | GCP |
|---|---|---|
| `1130\|2026-06-11` | 780 分 / 休憩 744 | **4,662 分 (3.2 日)** / 休憩 0 |
| `1194\|2026-06-17` | 523 分 / 休憩 70 | **1,453 分 (1.0 日)** / 休憩 60 |
| `1445\|2026-06-19` | 185 分 / 休憩 42 | **4,337 分 (3.0 日)** / 休憩 **4,096** |
| `1676\|2026-06-20` | 1,071 分 / 休憩 86 | **9,404 分 (6.5 日)** / 休憩 0 |

C の裏返し — **GCP 側で休息が欠けて勤務が閉じられなかった**形。休憩が 0 になるのは
`dtako_events` がその区間ごと落ちているため。`dtako` の 運行開始/運行終了 は push で
届いているので `has_operation` は true のままになり (`src/kosoku.rs:1254-1262`)、
**昼休憩の代替は入らずに休憩 0 になる** (`src/kosoku.rs:1618-1632`)。
再現: `..::losing_every_dtako_events_row_zeroes_break_instead_of_adding_lunch`。

`1445` の休憩 4,096 分 (68 時間) は R2 側に**閉じ損ねた `休憩` 区間**が在ることを示す。
`breaks_in` は上限を持たないのでそのまま拘束から引かれる。

この 4 行は `over_24h` が立っているはず (`restraint > 1440`、`src/kosoku.rs:1615`)。
**保存側でこのフラグを見れば、値を突合しなくても壊れた行を検出できる。**

### E — 拘束 1 分差 (1 行)

`PaperPerSegment` の紙丸めは**区分ごとに秒を切り捨てる**
(`src/kosoku.rs:1451-1546` の `paper_minutes_by_date` / `in_run_at`)。区分の切れ目は
運行イベントで決まるので、イベントが 1 件増減すると ±1 分ずれる。A〜D と同じ原因の
最小サイズ。

## 「どちらが正か」の判断材料

**自分では決めていません。** 材料だけ:

- **GCP が明らかに誤り**と言えるのは D の 4 行 (拘束 1.0〜6.5 日)。実在しない拘束で、
  改善基準の遵守チェックにも効く
- **基準 (オンプレ) が正とは限らない。** A の 29 行 (GCP の方が休憩が多い、合計
  +1,354 分) は、GCP にだけ在る `休憩` が本物なら**オンプレが実働を 1,354 分多く
  払っている**ことになる。C の 28 行も「GCP にだけ在る休息」で、休息が本物なら
  オンプレの `timecard` ラベルの方が実態と違う (値は同じなのでラベルだけの問題)
- **両方向に欠けている** = 「片方が新しい / 片方が古い」という単純な時間差では
  説明しきれない。少なくとも
  (i) alc/R2 の反映遅れ (#205-19 が特定した形。B / D がこれ) と
  (ii) MariaDB `dtako_events` 側にだけ無い行 (A / C) の 2 つが要る

## まだ確かめられていないこと (raw イベントが要る)

1. **乗務員 1021 の基準側の形が最後まで詰め切れていない。** 上の C の機構では
   「割った側 (基準) の割れ目はすべて 8 時間以上の運行の空き」でなければならないが、
   基準の `1021|06-26` は 13:26 → 16:57 の **3 時間 31 分**で割れている
   (`RUN_GAP_REST_MINUTES = 8h`、`src/kosoku.rs:1008`)。ここを割れるのは休息だけで、
   休息が在れば勤務はそこで閉じ 06-27 以降は `rest` になるはず — **基準側の入力に
   もう 1 つ何かある。** `GET /api/kintai/events?month=2026-06&driver=1021` (読み取り
   専用) の 1 リクエストで決着する
2. **両経路が同じ `logic_version` で走ったかを確認していない。** 「同じコード」は
   `kintai_fold.rs` の設計上そうなっているという読みで、実測ではない。
   オンプレ `/api/kintai/version` と `day_summaries.logic_version` の一致を見れば
   1 分で潰せる。**ここが割れていたら上の分析の前提そのものが変わる**
3. C の 28 行が「GCP にだけ在る休息」か「GCP にだけ在る**終業打刻**」かは、この
   2 本の JSON では区別できない (どちらでも勤務は同じ時刻で閉じる)。Postgres の
   `kintai.kintai_events` に 1021 の 06-21 17:44 前後の `終業` が在るかを見れば分かる

## 直すべきか

**この調査の範囲では `src/kosoku.rs` に直すところは無い** (#205-19 と同じ結論)。
入力が欠けたときに勤務を捏造せず、閉じられないものは捨てる / 閉じられるものだけ
閉じる、という現行の判断は意図どおり。

手を入れるとしたら入力側と検知側:

- **(検知) `over_24h` を fold の warning に出す。** D の 4 行は保存された時点で
  「拘束 6.5 日」と分かる。値の突合をしなくても月次で拾える最も安い網
- **(入力) `dtako_events` の両側の突合。** A / C は MariaDB 側に無い行が R2 に在る
  形なので、#205-13 / #205-16 の月ゲート (etags) だけでは拾えない
  (あちらは R2 の遅れを見る仕組み)

いずれも `src/kosoku*` / `src/kintai*` / `src/routes/kintai*` を触ると
`logic_version` が変わり全乗務員が stale になるので、**着手は親の判断待ち**。
