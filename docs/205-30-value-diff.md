- **D の 4 行も GCP が誤り。** 実在しない 1.0〜6.5 日の拘束

## 直すべきか

**`src/kosoku.rs` に直すところは無い** (#205-19 と同じ結論)。閉じられない勤務を
捏造せず捨てる/閉じる、という判断は意図どおりで、C も D も入力が欠けた結果。

直す先は入力側と検知側:

1. **(C の根治) push の窓を fold の窓に合わせる。** `push_month` が
   `exact_month_range` で書く限り、6 月の fold は 7 月の push に暗黙に依存する。
   窓を `month_range` に広げるか、fold が「読む窓ぶんの push が済んでいるか」を
   確かめて済んでいなければ **loud fail する**かのどちらか。
   **`exact_month_range` を選んだ理由は `src/kintai_push.rs:852-857` に書いてある**
   (翌月頭 2 日を「その 2 日しか見ていない状態」で署名すると毎回書き直しになる) ので、
   単純に広げるのは署名の設計と衝突する — **設計判断が要る**
2. **(D の検知) `over_24h` を fold の warning に出す。** 保存時点で
   「拘束 6.5 日」と分かる。値の突合をしなくても月次で拾える最も安い網
3. **(A / B) `dtako_events` の両側の突合。** 月ゲート (etags) は R2 の遅れしか
   見ないので、MariaDB 側にだけ無い行は拾えない

いずれも `src/kosoku*` / `src/kintai*` / `src/routes/kintai*` を触ると
`logic_version` が変わり全乗務員が stale になるので、**着手は親の判断待ち**。

# 欠落 143 行 — 最後の 1 運行がまるごと欠ける

**追記 (2026-07-31)。** 上の 65 行とは**別の原因**だった。当初は #205-19 / #205-29 の
担当としていたが、C の調査で作った replay harness がそのまま使えたのでここで決着させる。

## 結論

**GCP に無いのは「ある日以降のイベント」ではなく、`運行NO` 単位で
その乗務員の最後の 1 本がまるごと**である。

`dtako_events` を日付で切って GCP と一致する cutoff を探すと、**その cutoff が
最終運行の `unko_no` 先頭 6 桁 (= 運行開始日 `YYMMDD`) とぴったり一致する**。

| 乗務員 | 最終運行の開始日 | GCP と一致する cutoff | 一致 | 最終運行が覆う暦日 (行数) |
|---|---|---|---|---|
| 1078 | 2026-06-24 | **06-24** (ユニーク) | ✅ | 06-24〜07-01 (91 行) |
| 1517 | 2026-06-26 | **06-26** | ✅ | 06-26〜07-01 (140 行) |
| 1688 | 2026-06-28 | **06-28** (ユニーク) | ✅ | 06-28〜07-01 (77 行) |
| 1021 | 2026-06-19 | — (**欠落なし**) | — | 06-19〜07-01 (247 行) |

**1021 に欠落が無いのが対照になる** — 最終運行の CSV が取り込み済みだった 1 名だけ
欠落ゼロで、他の 3 名は最終運行ぶんが丸ごと消えている。つまり
**構造的な欠陥ではなく、fold を回した時点で最新の 1 運行がまだ届いていない
= 鮮度・順序の問題**。

1517 だけ cutoff がユニークに決まらない (06-20〜06-26 のどれでも一致する) のは、
**06-20〜06-25 にイベントが 1 件も無い**ため。運行単位で見れば「06-26 開始の
最終運行を落とす」の 1 通りに定まる。

## これ 1 つで、測定済みの 3 つの性質が全部説明できる

| 観測 (#205-29 の測定) | この機構での説明 |
|---|---|
| 欠落率が月末へ**単調上昇** (06-30 で 40.8%、月初は 1%) | 最後の運行は**月末を覆う**ので、消える暦日が月末に偏る |
| 影響 49 名のうち **44 名 (90%) が「ある日以降が全部消える」** | 消えるのが**連続した 1 運行ぶん**だから、その日以降が途切れずに消える |
| **`rest` 由来が 4 倍やられる** (rest 7.3% / timecard 1.8%) | 長距離の運行の尻尾は打刻が無く、勤務が `shifts_from_rest` で組まれる |
| **切れる日が乗務員ごとに違う** (共通 cutoff 無し) | **最後の運行の開始日が人によって違う**だけ |

## どう測ったか (追試の手順)

`tests/kintai_205_30_replay_test.rs` (このリポジトリに在る) を使う。**本番データは
リポジトリに置かない**ので、生イベントは読み取り専用の口から都度取る。

1. `GET /api/kintai/events?month=2026-06&driver=<CD>` の応答を保存する
2. **そのまま畳んで基準と一致するか**を先に確かめる (harness の正しさの確認):
   `REPLAY_EVENTS=<生イベント> REPLAY_EXPECT=<基準 JSON> REPLAY_DRIVER=<CD>`
   → 1078 / 1517 / 1688 / 1021 の**4 名すべてで完全一致**した
3. `source = "dtako_events"` の行を `datetime >= <日付>` で落とした入力を作り、
   **GCP 側の JSON と一致する日付を探す**
4. 見つかった日付を、その乗務員の**最終 `unko_no` の先頭 6 桁**と突き合わせる

**1078 の 06-24 は #205-19 が別セッション・別ハーネスで出した値と一致した**
(独立再現)。同じ数字が違う道筋で出るのは、機構が本物であることのかなり強い証拠。

## ★ 棄却した仮説と、その根拠

**ここが一番重要。** 6 月の 142 行差については以下は**すべて原因ではない**。
根拠つきで残すので、**同じ仮説を再度追わないこと**。

### 1. `has_kudgivt = FALSE` で運行が split されない → **棄却**

本番の `unsplit` の口で実測して **`unsplit_total: 0`**。未 split の運行は 1 件も無い。

**ただし「再アップロードで `has_kudgivt` が `DEFAULT FALSE` に戻る」バグ自体は実在する。**
#205-28 が突き止め、`ippoan/rust-alc-api#586` で修正済み。
**バグは本物だが、6 月の 142 行差の原因ではない** — 両方を混同しないこと。

### 2. push と fold の窓ずれ → **欠落の原因としては棄却 (反転 28 行の原因としては確定)**

`PUSHED_SOURCES` (`timecard` / `dtako`) の行を `2026-07-01` 以降で落として
GCP と突き合わせると、**1078 / 1517 / 1688 のいずれも一致しない** (行数が 1 行も減らない)。

- **1517 は 07-01 以降の打刻が 0 件**。最終 始業 06-26 の相手の終業は `month_range`
  の外 (07-02 以降) にあり、**オンプレ側も見ていない**
- **1688 は `timecard` の行が 1 行も無い** (612 行すべて `dtako_events`)

本番でも裏が取れている: **1〜7 月の打刻を全部 push した後に 6 月を畳み直しても
`day_summaries` は 3,230 → 3,233 の +3 のみ。**

⇒ 「月内に対の無い始業がある」は窓ずれの**必要条件であって十分条件ではない**。
効くのは**終業が `07-01` という 1 日の隙間にちょうど落ちたとき**だけで、1021 は
当たり、1517 は当たらなかった。**窓ずれで確定しているのは反転 28 行だけ**
(上の C。1021 で両側を完全再現済み)。

### 3. R2 に CSV が無い (upload 未完了) → **棄却**

入力欠け検知の実測で **`etag無=0`**。「DB に運行があるのに R2 に CSV が無い」形ではない。

### 4. `n=1130` は運行数として少なすぎる → **棄却**

**長距離は 1 運行が数日〜10 日を覆う**ので、1 乗務員あたり月 **3〜8 本**しかない
(実測: 1021 = 4 本 / 1517 = 3 本 / 1078 = 5 本 / 1688 = 8 本)。平均 5 本なら
**137 名 × 2.4 か月 ≒ 1,644 本**で、1,130 と同オーダー。
「運行そのものが `dtako_operations` に入っていない」の根拠にはならない。

### 5. 「73 名の末尾が 37 日超」 → **手元データには出ない。検知側の母集団を疑うべき**

`2026-07-01` を期待日として、最終勤務日からの日数を数えた結果:

「大半の乗務員は 6 月末まで運行している」と言っている**ので、同じデータから
「73 名が 37 日超」にはならない。

**母集団を疑うこと** — 警告は **137 名**、6 月に勤務のある乗務員は **132 名**。
tail gap を**乗務員マスタ全件**で回していれば、退職者・長期離脱者が全員
「37 日超」に入る。**73 名のうち「6 月の `day_summaries` に 1 行も無い乗務員」が
何名いるかを見れば一発で分かる。**
